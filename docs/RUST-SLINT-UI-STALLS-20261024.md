# Задержки UI при локальной генерации: разбор 24 октября 2026

Поручение: разобрать редкие задержки до 740 мс, исправить подтверждённые причины и проверить результат без Computer Use и ручного участия. Рабочая установка, личная база, автозапуск и аудиоустройства не изменяются.

**Результат:** подготовлен и проверен **0.1.18**. В двух итоговых реальных GPU-прогонах — **4 700 активных кадров, p95 10,207 мс, максимум 14,579 мс, 0 кадров >100 мс**. Созданы и декодированы шесть записей; отмена следующей задачи заняла 310/546 мс. DPC-нагрузка CPU0 в первом прогоне сохранилась до 100%. Инженерный обход подтверждён в этом программном сценарии на указанном ПК. Весь P8 и stable не закрываются; проверка заметности в обычном окне отложена. 0.1.17 с одной ideal hint не прошёл повтор и не является исправлением.

## Что именно задерживалось

Замеряет отдельный release-процесс: настоящее `AppWindow`, сервис настроек, локальные Gemma 4 12B и CosyVoice 3. Другой поток ставит переключение страницы в очередь; UI рассчитывает и полностью рисует кадр 1100×780 в памяти. Интервал запросов — 50 мс, одновременно ожидает только одно действие. Есть 60 секунд прогрева, 100 кадров до ML, создание трёх записей, запуск и отмена следующей задачи, 100 кадров после отмены. Записи декодируются в PCM, playback отсутствует. Новая синтетическая библиотека создаётся под `work/`; выбранные установленные среды и веса повторно используются. Источник личного пресета не входит в отчёт и пакет.

Это задержка реакции/рисования UI, а не длительность синтеза фразы. Часть выбросов приходилась на незапрошенную перерисовку перед обработкой очереди, поэтому отдельно измерены dispatch, render, CPU именно UI-потока и независимый watchdog. Watchdog не приостанавливает поток; диагностические stack-прогоны с краткой приостановкой собственного UI не считаются приёмочными замерами.

Оборудование: Windows 11 Pro x64 26300, Ryzen 9 3900X (24 логических CPU), 68 614 680 576 байт доступной ОС физической RAM, RTX 4080 SUPER, драйвер Windows `32.0.16.1742`. Это не целевой ноутбук с 8 ГБ RAM.

В каждом из перечисленных завершённых ML-прогонов созданы и декодированы три записи. Для A/B использован один и тот же `app.exe` 0.1.16, SHA-256 `eba930598d104492ab70e97a7a1a34d0566d8d24ddd17716157fb567b15d93d8`; исключение — исходные 0.1.13/0.1.15 и отдельный Python batch-эксперимент. В A/B размещение менялось только у собственного первого UI-потока через проверенный PID/TID, без изменения системной маски. Показания и реальные маски сохранены в `.affinity.json`; основной процесс сохранял `0xffffff`.

`gpu-small-batch-01.dpc.json`: независимые read-only PDH-счётчики с интервалом около 100 мс. В окне 65–115 секунд DPC занимали CPU0 в среднем **61,15%**, 144 отсчёта превышали 90%, максимум — 100%. В остальных ядрах максимальный отсчёт DPC — около 31%. До генерации среднее CPU0 составляло 7,21%. Длинные UI-кадры приходились на 87,25 / 94,12 / 105,47 секунды. В watchdog при длинном render CPU UI почти не рос, watcher продолжал работать, pending I/O отсутствовал, не наблюдалось соответствующего роста чтения/страничных ошибок; свободной RAM оставались десятки ГБ.

Это сильное подтверждение участия DPC/планирования на перегруженном CPU0; обратный контроль существенно усиливает вывод по сравнению с одним удачным прогоном. **Конкретный драйвер и его функция не установлены.** Нельзя честно приписать задержку определённой функции NVIDIA, Slint или файловому mutex. Системная WPR-трасса CSwitch/DPC не стартовала: Windows отказала в праве профилирования (`0xc5585011`); права и системные политики не менялись. Разреженные release-символы и запоздавшие stack-снимки не выдаются за точный стек причины.

0.1.17 добавил номер CPU в начале фазы. Оба длинных dispatch ожидали предыдущую перерисовку: watchdog зафиксировал начало render на **CPU0**, длительность фаз до 278/256 мс, неизменный CPU time UI; после завершения поток уже был на другом ядре. Синхронизированные по Unix-якорю PDH-отсчёты в обоих окнах (87,7 и 94,95 с) достигали **100% DPC CPU0**. Одной `SetThreadIdealProcessor` оказалось недостаточно: Windows вправе выполнить поток на другом ядре.

В итоговом 0.1.18 первый PDH-прогон содержит 2 180 отсчётов, из них **195 с DPC CPU0 >90%**, максимум 100%. Исправленный UI продолжил рисовать кадры без выбросов >100 мс при наличии этой нагрузки. В обоих итоговых прогонах применены 23 CPU Sets; ядро до/после каждого измеренного активного render и начало длинных фаз watchdog не были CPU0. Системная маска affinity не менялась. Это проверено `final-integrity.py`, а не выведено только из успешного возврата Win32 API.

## Изменения приложения

- `Job::assign_background` назначает вычислительное дерево в Below Normal до передачи задания. UI остаётся Normal. Это устраняет отдельную подтверждённую конкуренцию CPU: контролируемая нагрузка на одном разрешённом ядре дала p95 1 491 мс до / 5,997 мс после, максимум 1 543 / 30,501 мс (`contention-01/result.json`). Тестовая нагрузка не поставляется пользователю.
- `UiScheduling` задаёт **CPU Sets только UI-потоку**, исключая CPU0 на подходящей одногрупповой системе с минимум четырьмя разрешёнными CPU. Для UI сохраняется выбор между остальными разрешёнными ядрами и управление парковкой Windows; вычислительное дерево продолжает использовать все свои ядра. Явные thread/process CPU Sets пользователя не переопределяются, hard affinity mask и приоритет UI не меняются. Многогрупповые системы, узкие пользовательские маски и отсутствие подходящих ядер обход не получают. Дополнительная ideal hint выбирает производительную efficiency class и доступное ненулевое ядро. Ошибка запроса оставляет обычную политику ОС; guard восстанавливает наследование CPU Sets и прежнее предпочтение при завершении. Гибридная топология проверена синтетически, отдельного физического устройства не было.
- Исправлен реальный CPU-сбой CosyVoice при повторном использовании CUDA-среды: `CUDA_VISIBLE_DEVICES=-1` выставляется до тяжёлых импортов. На Windows пустое значение удаляло native-переменную, хотя Python показывал её пустой; CUDA и Python/NVML расходились. Нативный regression и полный CPU-прогон подтверждают исправление. Аргументы llama CPU/GPU batching восстановлены без изменений прежнего пользовательского файла.
- Расширена только opt-in диагностика `--measure-frames`: CPU/IO/страничные ошибки, независимый watchdog, ядро до/после render, Unix-якорь времени и применённая scheduling hint. В обычном приложении нет 2-мс watchdog или фонового PDH-мониторинга.

Основания API: [мягкое предпочтение и предостережение о жёсткой affinity](https://learn.microsoft.com/en-us/windows/win32/procthread/multiple-processors), [CPU sets и существующие ограничения](https://learn.microsoft.com/en-us/windows/win32/procthread/cpu-sets), [флаги и efficiency class CPU](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winnt/ns-winnt-system_cpu_set_information.md), [CUDA environment variables PyTorch](https://docs.pytorch.org/docs/2.9/cuda_environment_variables.html). Мягкая рекомендация не даёт гарантии выбора ядра; ОС сохраняет последнее решение.
